# Implementation prompt — VASA coded-value → WHO-canonical decoding service (in-place, with UI display)

---

## Role and objective

You are implementing a **value-decoding service** inside VACMS (`va_explorer.va_data_management`).
Its job: for the VASA instrument (form ID `znphi_vasa_who_2016`), translate the
**coded answers** that arrive in the VASA CSV/ODK export (e.g. `1`, `2`, `8`, `9`,
space-separated multi-selects like `2 3`) into their **decoded values**, and adopt
those decoded values **in place**.

**Decode target = WHO-canonical choice names** (e.g. `male`, `female`, `yes`, `no`,
`dk`, `ref`), i.e. the value space required by pyCrossVA/InterVA5 and already defined
by the generated `VALUE_CROSSWALK` (`Architecture.txt` §3.4). These WHO-canonical
values **replace the raw VASA codes in place** on the canonical answer fields — they
are **not** stored as a separate VASA-label representation.

Two concrete requirements:

1. **In-place adoption.** Decode each VASA coded answer to its WHO-canonical name and
   store it on the record's canonical `Idxxxxx` / helper fields (the same fields
   coding consumes). The raw code is replaced by the WHO-canonical value.
2. **UI display.** The VACMS UI (unified VA/VASA line list and the VASA record-detail
   view, plus any place answers are shown/exported) must **display these decoded
   WHO-canonical values**, never the raw numeric codes.

The decoder must be wired into the existing VASA ingestion path
(`va_explorer/va_data_management/utils/vasa_loading.py`).

## 1. Background you must internalise before coding

Read `Architecture.txt` (esp. §2.1, §3.1–§3.4, §4.1, §5.1) and confirm in code before
you start:

- VASA `name` values are pseudo-names (`Q1601`, `N2001`, `C3001`, `A4001`, …); the
  XLSForm carries a `WHO_name` column mapping them to WHO IDs. **Field-name
  translation is out of scope for this task** — you are decoding *answers*, not
  renaming *fields*. The field map (`PSEUDO_TO_WHO`) is assumed to already place the
  answer on the correct canonical field.
- Many VASA select answers are numeric codes. **The code→value mapping is
  field-specific** (via the field's referenced choice list). A global `1=yes / 2=no`
  decoder is forbidden: it would corrupt sex, marital status, units, tobacco, and
  dozens of other lists (`Architecture.txt` §6.2).
- The existing loader already decodes VASA codes to **WHO-canonical names** via the
  generated `VALUE_CROSSWALK` (`vasa/field_map.py`) and stores them on the `VASA`
  model's `Idxxxxx` fields; `build_pycrossva_records()` sends those to coding
  (`Architecture.txt` §3.4, §4.1 step 3, §5.1). **This task hardens, owns, and
  surfaces that decoding** — reuse `VALUE_CROSSWALK`; do not invent a parallel
  scheme.

### XLSForm structure you will parse

The VASA XLSForm (`znphi_vasa_who_2016.xlsx`) is a standard XLSForm workbook with (at
least) these sheets/columns:

- `survey` — columns include `type`, `name`, `label`, `WHO_name`.
  - `type` is a plain type (`text`, `integer`, `calculate`, `note`, `date`, …) or a
    select declaration: `select_one <list_name>` / `select_multiple <list_name>`.
    The token after the select keyword is the choice `list_name`.
- `choices` — columns include `list_name`, `name` (the stored **code**, e.g. `1`,
  `2`, `8`, `9`), and `label` (human-readable text; the header may be
  language-suffixed, e.g. `label::English (en)`).

> Confirm exact header spellings by opening the workbook (openpyxl / pandas) — do not
> assume. Fail loudly if `survey`/`choices` or required columns are absent.

### How WHO-canonical names are derived (reuse existing generator)

Per `Architecture.txt` §3.4, the crosswalk is generated by, for each mapped VASA
select field: taking its VASA choice list, taking the **target WHO field's** choice
list, normalising English labels, reconciling known spelling variants, and emitting
`VASA code → WHO choice name` where labels match. Reuse this generated
`VALUE_CROSSWALK` (and its `generate_vasa_mapping` command). Do not rebuild a separate
label index.

## 2. Deliverables

1. **Reuse / harden the generated `VALUE_CROSSWALK`** (`vasa/field_map.py`,
   `generate_vasa_mapping`) as the single source of truth for VASA code →

2. A **decoder module/service** (e.g. `vasa/value_decode.py`) exposing pure,

   ```python
   def decode_value(field_name, raw_value) -> DecodeResult
   def decode_row(row: dict) -> dict[str, DecodeResult]
   ```

   `DecodeResult` carries `raw`, `decoded` (WHO-canonical), `field_rule`
   (`select_one` | `select_multiple` | `not_a_select`), and `value_rule`
   (`crosswalk` | `fallback` | `unknown_code` | `blank` | `already_canonical`), plus
   per-token results for multi-select.
3. **In-place adoption in `utils/vasa_loading.py`** (§4): decoded WHO-canonical
   values are written to the canonical `Idxxxxx`/helper fields, replacing raw codes.
4. **UI display** of decoded WHO-canonical values in the line list, record-detail
   view, and exports (§5).
5. **Raw-value provenance** so a re-decode after a crosswalk change is auditable
   (§4, `Architecture.txt` §7 gap 1).
6. **Tests** (§6) and a short docs note.

## 3. Decoding rules and edge cases (be exhaustive)

- **`select_one`:** trim the raw string; look up the field-specific
  `VALUE_CROSSWALK` entry (`VASA code → WHO name`). Exact string match on the
  stringified code.
- **`select_multiple`:** split the raw value on **whitespace** (ODK exports
  multi-selects space-separated, e.g. `2 3`), decode each token to its WHO name, then
  **join the WHO names with commas** to match VACMS's `MultiSelectField` convention
  (`Architecture.txt` §3.4).
- **Blank / missing:** empty or absent → `value_rule = blank`; leave the canonical
  field blank (a blank is the same missing-answer representation coding already
  expects). **Do not treat `"0"` as blank** — `0` may be a genuine coded answer
  (`Architecture.txt` §6.3).
- **Unknown code** (token absent from the field's crosswalk): **retain the raw code**
  in place, set `value_rule = unknown_code`, and raise a non-blocking
  `DataQualityIssue`. Never fabricate a value. (This matches current behaviour —
  `Architecture.txt` §3.4 — but must be made observable; §7.)
- **Generation fallback:** if the crosswalk itself emitted a normalised-label
  fallback (no WHO label matched at generation time), flag `value_rule = fallback`
  and surface it — such a value is present but may not be recognised by pyCrossVA
  (`Architecture.txt` §3.4, §7 gap 3).
- **Idempotency:** a value already equal to a valid WHO-canonical name for the field
  passes through as `already_canonical`; never double-decode.
- **Field-specificity:** decode strictly via the field's own crosswalk entry — never
  a global `1=yes` rule.
- **Do not apply** the `Q1202` / `N2005` semantic split or `PSEUDO_TO_WHO` renaming
  here — those remain in their existing loader steps; this service only decodes
  answer values.

## 4. In-place adoption in `utils/vasa_loading.py`

The shared loader (`Architecture.txt` §4.1) already, per source row: composes GPS →
looks up `PSEUDO_TO_WHO` → **decodes selects via `VALUE_CROSSWALK`** → coalesces
duplicate WHO targets → applies `Q1202`/`N2005` splits → copies admin/location →
normalises identifiers → detects instrument → parses dates → routes social fields →
upserts.

Own and harden the decode step so that:

1. Each VASA select answer is decoded to its WHO-canonical name and **stored in place
   on the canonical `Idxxxxx`/helper field** (replacing the raw code). Because these
   are exactly the values `build_pycrossva_records()` sends to coding, in-place
   adoption is **coding-safe by construction** — decoded value == stored value ==
   coding input.
2. **Preserve the raw code as provenance** (recommended: a `raw_answers`
   JSON/`JSONField` on `VASA`, or a staging/provenance record) so a new crosswalk
   version can be replayed and audited. This closes the "no raw-answer ledger" gap
   (`Architecture.txt` §7 gap 1). Add a migration for whatever you introduce.
3. Respect the existing **blank/upsert policy** (`Architecture.txt` §4.1, §7 gap 2):
   only meaningful incoming values update the record; an empty re-import must **not**
   clear a previously stored decoded value.
4. Keep decode **idempotent** (already-canonical values pass through) and route
   unknown/fallback codes to `DataQualityIssue` (§7).

Do this in the same per-row transaction/upsert so decoded values, provenance, and
canonical answers stay consistent for the record.

## 5. UI display of decoded values

The UI must present the **decoded WHO-canonical values**, never raw numeric codes.

- **Unified VA/VASA line list** and **VASA record-detail view** (`va_data_management`
  views): render answers from the canonical `Idxxxxx`/helper fields (now WHO-canonical
  after §4). Confirm no template/serializer path still shows raw codes for VASA.
- **Exports / analytics** that surface answer values must use the decoded values.
  (Note `Architecture.txt` §7 gaps 10–11: VASA export/DHIS are currently traditional-VA
  only; if you extend any VASA-facing view or export, it must show decoded values.)
- Because the stored canonical value *is* the WHO-canonical name (e.g. `female`,
  `yes`), no display-time decode lookup is needed — the UI reads the field directly.
  If a friendlier human label is later wanted, add an **optional, display-only**
  WHO-name → label lookup at render time; it must not change stored values or coding
  input, and it is not required by this task.
- Add a regression check (§6) that a rendered VASA record shows decoded values and
  contains no bare numeric codes for known select fields.

## 6. Tests and acceptance criteria

Add tests alongside `va_data_management/tests/test_vasa_*.py`:

- **Direct decode:** `Q1601="2"` (sex → `Id10019`) → `female`; `="1"` → `male`.
- **Yes/no + special codes:** `A4006` (→ `Id10064`) codes `1/2/8/9` →
  `yes / no / ref / dk` (verify exact WHO names against the crosswalk/WHO choices).
- **Cross-section duplicate concept:** `N2001` and `C3001` both → `Id10354`, codes
  `1/2/8/9` → `yes/no/ref/dk`.
- **`select_multiple`:** `"2 3"` → the two WHO names joined by commas, order
  preserved.
- **Unknown code:** raw retained in place, `value_rule=unknown_code`, one
  `DataQualityIssue` raised.
- **Fallback value:** a crosswalk fallback entry is flagged `fallback` and surfaced.
- **Blank vs zero:** `""` → blank; `"0"` → decoded per crosswalk (not treated as
  blank).
- **Idempotency:** decoding an already-canonical value is a no-op; re-running the
  same load changes nothing.
- **Non-select passthrough:** `Cal_Q1601`, `cal_*`, `deviceid`, dates, free text are
  untouched.
- **Coding parity:** pyCrossVA input for a VASA record equals its
  canonical-VA equivalent for the same answers (`Architecture.txt` §6.5) — i.e. the
  in-place decoded values are exactly what coding receives.
- **UI:** a rendered VASA line-list row and detail view show decoded WHO-canonical
  values and no raw numeric codes for known select fields.
- **Provenance:** raw code is retrievable after decode; a crosswalk-version bump can
  replay decoding from raw.
- **Domain coverage:** every accepted source code for every mapped select field
  produces a value allowed by the target WHO choice list (`Architecture.txt` §6.5).
- **Index drift:** `generate_vasa_mapping --check` passes on committed artifacts and
  fails on an un-regenerated XLSForm change.

## 7. Logging, data quality, and observability

- Route `unknown_code` and `fallback` occurrences to `DataQualityIssue` with field
  name, raw value, `list_name`/WHO target, and record identity. Non-blocking;
  self-resolving on correction.
- Per-batch summary: rows decoded, fields decoded, unknown-code count, fallback
  count, non-select passthroughs. Uphold the batch invariants in
  `Architecture.txt` §6.4: no source column silently dropped, no answer silently
  overwritten with a *different* value, decode idempotent.
- Version decoded output by the crosswalk/XLSForm hash for auditability.
